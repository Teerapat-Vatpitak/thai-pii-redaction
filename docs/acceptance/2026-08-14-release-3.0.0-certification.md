no unique meaningful or unclear-owner work and were classified SAFE TO DELETE.

## Release workflow safeguards

The first frozen candidate, `1620217e6739208e558bd26b662bc67960cd764b`,
passed its exact-SHA CI and manual release build but is **invalidated and must
not be tagged**. Three independent reviews found that tag-mode provenance was
not closed over current-run bytes, Tauri could download mutable Linux bundling
helpers, final production macOS/Linux packages were not executed, and public
side-panel retention wording was inaccurate. The replacement gates below are
part of the candidate rather than post-publication follow-up.

- The former intentional authorization stop is removed because this task is
  owner-authorized; tag publication is still not automatic.
- The Linux wrapper preserves the exact pre-`linuxdeploy` backend, runs Tauri,
  finalizes the AppImage with the checksum-pinned output plugin, deletes any
  stale signature for the pre-final byte stream, signs the finalized AppImage,
  and requires the new signature before the action discovers assets.
- All five Tauri Linux helper downloads are replaced with immutable URL,
  size, and SHA-256 pins. `linuxdeploy` is pre-normalized for Tauri's
  unconditional three-byte header rewrite, and the exact closed cache must be
  unchanged after bundling. The AppImage output-plugin asset ID remains
  `497460911` with SHA-256
  `a45d3e227bc7f397e9cf6bfa4c9507494efa2293357b6e86690a3de2ca992e79`.
- Release validation requires signatures for Windows setup, macOS updater
  archive, DEB, and AppImage. It production-smokes exact final NSIS, both macOS
  payloads, DEB, and finalized AppImage bytes before staging.
- Tag mode downloads the Desktop files from the same workflow run into a
  source/tree/run-bound closed manifest, regenerates canonical `latest.json`,
  resolves one exact draft by tag, rejects extras, compares every draft digest,
  then redownloads and rechecks the final `SHA256SUMS` set before provenance.
- The Extension package fixes ZIP timestamps, ordering, compression, creator
  system, and regular-file modes. Repeated local packages are byte-identical.
  Branch CI retains the exact production-ID ZIP and its digest for 30 days.
- A manual pre-tag release mode accepts an exact full commit SHA, verifies the
  checkout and clean tree, runs the same production platform build without a
  tag or Release, retains all ten Desktop/signature/Extension files, and emits a
  deterministic closed-set manifest binding every size and SHA-256 to the
  source commit/tree, workflow run/attempt, and producing job. Tag mode remains
  the only path that creates a draft.

## Privacy and signing classification

The release changes no core detection, vault, provider, or mapping ownership
boundary. Desktop and Extension continue to hold only broker scopes/session
handles; mappings and private-backend credentials remain outside storefront
JavaScript. The live side-panel document can retain raw input/reply and displayed
masked/restored values until the user clears or replaces them, or the panel is
closed/reloaded; AI Guard does not deliberately persist those values in Chrome
storage or on disk. Release evidence uses synthetic/value-free data and must not
retain raw PII, mappings, credentials, provider bodies, or restored answers.

Windows remains unsigned under the accepted direct-distribution policy. The
local certificate store contains no usable code-signing identity. macOS is
unsigned and not notarized because no Apple signing/notarization configuration
is present. Those states must be disclosed, not described as green publisher
attestation. Tauri updater signatures are mandatory byte-authentication but do
not replace Authenticode, Apple signing, or notarization. Only secret *names*
were inspected; no secret value is recorded here.

The production Extension identity is
`kdjmkknedgmfphpkjhjdhmjadaelgggm`, with the one exact admitted Chrome origin
defined by public configuration. Prior evidence classifies its Web Store item
as Draft/unpublished. Current live store access and status must be checked
before exact-ZIP submission; pending store review does not convert unpacked
browser evidence into Web Store installation.

## Remaining certification gates

Before the candidate can be called released:

1. freeze an immutable branch commit and pass every CI and cross-platform job;
2. retain and hash the exact candidate artifact manifest, including the
   production Extension ZIP;
3. obtain three independent read-only reviews on that exact commit/tree and
   manifest: security/privacy, package/release, and Extension/documentation;
4. preserve reviewed-tree equality while squashing to `main`, then pass every
   post-main CI and cross-platform job;
5. tag exact green `main` as `v3.0.0`, let the workflow build a draft, and verify
   every expected exact asset, checksum, signature, provenance statement, and
   updater reference;
6. exercise clean install, 2.5.0-to-3.0.0 upgrade, launch/smoke, and uninstall
   with the exact Windows draft artifact, with value-free cleanup evidence;
7. publish the verified GitHub draft and confirm release URLs/metadata; and
8. inspect the live Chrome Web Store item and, when authenticated and accepted
   by the store, submit the exact reviewed ZIP without claiming approval before
   the store reports it.

Any failed exact-source/package gate keeps the release blocked. Store review
pending after an accepted exact-ZIP submission is an external publication state,
not a Desktop release blocker.
