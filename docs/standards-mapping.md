# การจับคู่ความสามารถของ AI Guard กับ ISO/IEC 20889:2018 และ มรด. 6:2566

จัดทำ 2026-08-01 (Track D ข้อ 4 ใน [ROADMAP](../ROADMAP.md))

## สถานะของเอกสารนี้

เอกสารนี้อธิบายว่า **สิ่งที่ AI Guard ทำอยู่จริงในโค้ด** ตรงกับศัพท์และการจัดหมวด
เทคนิคของมาตรฐานสองฉบับอย่างไร เป็นการจับคู่เชิงศัพท์และเชิงความสามารถ
(correspondence) เท่านั้น **ไม่ใช่คำประกาศ conformance ไม่ใช่การรับรอง และไม่มี
หน่วยงานใดตรวจประเมิน** ทุกข้อความอ้างอิงสิ่งที่ implement แล้วในโค้ด ไม่อ้างสิ่งที่
มาตรฐานแนะนำแต่ยังไม่ได้ทำ

## ส่วนที่ 1 การจับคู่กับ ISO/IEC 20889:2018

### 1.1 ศัพท์ของมาตรฐานที่ตรงกับสิ่งที่ระบบทำ

| สิ่งที่ AI Guard ทำ (โมดูล) | ศัพท์/นิยาม ISO 20889 | หมายเหตุความตรง |
|---|---|---|
| ตรวจจับ PII แบบ structured ด้วย regex + checksum เช่น เลขบัตรประชาชน 13 หลัก เบอร์โทร อีเมล (`pii_redactor/detectors/` ฝั่ง FP) | **direct identifier (3.10)** attribute เดียวที่ระบุตัวบุคคลได้ใน operational context | ตรงตามนิยาม ค่าเหล่านี้ระบุตัวได้ด้วยตัวเอง |
| ตรวจจับชื่อ ที่อยู่ องค์กร วันที่ ด้วย NER + cue (ฝั่ง TB) | **indirect identifier (3.16)** / **quasi-identifier (3.28)** attribute ที่ระบุตัวได้เมื่อประกอบกับ attribute อื่น | ระบบเก็บ ORGANIZATION/LOCATION/DATE ไว้ mask ในฐานะ quasi-identifier โดยเจตนา |
| ธงหมวดอ่อนไหวมาตรา 26 (`report.scan_section26` + `sensitive_detector`) แจ้งเตือนอย่างเดียว ไม่ redact อัตโนมัติ | **sensitive attribute (3.34)** ซึ่ง Note ของนิยามระบุว่าการกำหนดว่าอะไรอ่อนไหวขึ้นกับบริบทการใช้งาน | มาตรฐานเองบอกว่า designation เป็น input ของการออกแบบ ไม่ใช่สิ่งที่บังคับ redact ตรงกับนโยบาย flag-only ของระบบ |
| โหมด token แทนค่า PII ด้วย `[ชื่อ_1]` และเก็บ mapping ใน `SessionVault` ในหน่วยความจำ (`anonymizer/` + `session_vault.py`) | **pseudonym (3.26)** / **pseudonymization (3.27)** แทน identifier ของ data principal ด้วย pseudonym เพื่อซ่อนตัวตน | ตรงตามนิยาม 3.27 ตรง ๆ สอดคล้องหัวข้อ 9.4 (Pseudonymization techniques — อ้างระดับชื่อหัวข้อ) local `SessionService` ถือ mapping ต่อ session ส่วน stateless path ถือชั่วคราวต่อ request; HTTP v1 ยัง project field ที่ประกอบ mapping ไปยัง response ของ client ซึ่งเป็นช่องว่างที่เปิดอยู่ |
| โหมด surrogate สร้างค่าปลอมรูปแบบถูกต้อง เช่น เลขบัตรที่ผ่าน mod-11 ชื่อไทยจาก pool ในเครื่อง (`fp_generator.py` / `tb_generator.py`) | ยังเป็น **pseudonymization (3.27)** โดย pseudonym มีรูปแบบเหมือนค่าจริง | **ไม่ใช่** format-preserving encryption (หัวข้อ 9.2.4 — อ้างระดับชื่อหัวข้อ) เพราะ generator ของระบบไม่ใช้กุญแจเข้ารหัสใด ๆ และตัวค่าปลอมถอดกลับเป็นค่าจริงไม่ได้ การกู้คืนทำได้ทางเดียวคือผ่าน vault |
| ทาดำ PDF ระดับ bbox แล้ว flatten เพื่อลบ text layer เดิมออกจากไฟล์ผลลัพธ์ (`redactor.py` ผ่าน `/api/redact-pdf`) | ใกล้เคียงตระกูล **suppression** (หัวข้อ 9.3 — อ้างระดับชื่อหัวข้อ นิยามละเอียดของหัวข้อนี้อยู่นอกส่วนที่เข้าถึงได้) | ปัจจุบันการเลือก bbox ยังจับคู่ fragment ทั้งเอกสาร ไม่ผูกกับ `Entity.span` และข้าม bbox หนึ่งอักขระ จึงยังรับประกันไม่ได้ว่า pixel ของ PII ทุกตำแหน่งถูกปิดบัง; exact-alignment และ negative-pixel gate ยังเปิดอยู่ |
| กู้คืนคำตอบ AI กลับเป็นค่าจริงผ่าน reverse index ของ vault (`reverse_mapper.py`) | **re-identification (3.31)** ที่ผู้ควบคุมทำเองโดยชอบ สอดคล้องเชิงชื่อกับหัวข้อ 12.4 Controlled re-identification (อ้างระดับชื่อหัวข้อ) | local multi-turn path กู้คืนได้ในเครื่องขณะที่ session vault ยังอยู่; hosted/stateless roundtrip กู้คืนชั่วคราวภายใน backend container ใน request เดียว |
| คะแนนความเสี่ยง re-identification จาก quasi-identifier (`reid_risk.py` โมเดลตระกูล Sweeney) | **re-identification risk (3.33)** / **singling out (3.35)** | เป็น heuristic score **ไม่ใช่** formal privacy measurement model (3.3) และ**ไม่ใช่**การรับประกัน K-anonymity (3.18) ระบบไม่ควบคุม dataset ทั้งชุดจึงพิสูจน์ K ไม่ได้ |
| pre-send leak guard สแกนซ้ำก่อนส่งออกใน CLI `send_to_ai` (`ai_client._validate_pre_send` + `leak_guard.py`) | มาตรการเชิงเทคนิคเสริม **de-identification process (3.6)** | HTTP/worker roundtrip ปัจจุบันยังเรียก provider ต่อได้หลัง residual warning; การรวม outbound policy ให้ fail closed ทุก adapter เป็น gate ที่ยังเปิดอยู่ |

### 1.2 ขอบเขตชนิดข้อมูลที่ต่างกัน และเหตุที่ยังจับคู่ได้

ISO 20889 ระบุใน Introduction และ Clause 6 ว่ามาตรฐาน focus ที่ **structured
datasets** ที่มองเป็นตารางได้ และบอกเองว่าเทคนิคอาจไม่ apply กับข้อมูลซับซ้อน
เช่น free-form text โดยชี้ไปที่ **Annex C (De-identification of free-form text)**
ว่าอธิบายว่าเทคนิคที่เลือกไว้ใช้กับ free-form text ได้อย่างไร (เนื้อ Annex C
อยู่นอกส่วนที่เข้าถึงได้ จึงอ้างเพียงว่ามาตรฐานรับรู้กรณีนี้และมีภาคผนวกรองรับ)

AI Guard ทำงานกับ free-form text ภาษาไทยและเอกสาร PDF เป็นหลัก ไม่ใช่ตาราง
การจับคู่ในเอกสารนี้จึงอยู่ที่ระดับ**นิยามศัพท์และตระกูลเทคนิค** (สิ่งที่ระบบทำคือ
pseudonymization ตามนิยาม 3.27 และการลบค่าออกจากเอกสารซึ่งใกล้เคียงตระกูล
suppression ตามชื่อหัวข้อ 9.3) ไม่ใช่การอ้างว่าปฏิบัติตามกระบวนการเชิงตารางของ
Clause 9-11

### 1.3 สิ่งที่ระบบไม่ได้ทำ (ตามการจัดหมวดของมาตรฐาน)

เพื่อกันการอ่านเกิน ระบบ**ไม่ได้** implement เทคนิคต่อไปนี้ (อ้างระดับชื่อหัวข้อจาก
สารบัญ) statistical tools (9.1 sampling/aggregation), cryptographic tools (9.2
ทุกแบบ รวม deterministic/order-preserving/format-preserving/homomorphic),
anatomization (9.5), generalization (9.6), randomization (9.7
noise/permutation/microaggregation), synthetic data (9.8) และ**ไม่มี** formal
privacy measurement model ใด ๆ ของ Clause 10 (K-anonymity, L-diversity,
T-closeness, differential privacy, linear sensitivity) คะแนนความเสี่ยงของระบบ
เป็น heuristic ไม่ใช่ guarantee

## ส่วนที่ 2 การจับคู่กับ มรด. 6:2566

มรด. 6:2566 เป็นแนวปฏิบัติสำหรับหน่วยงานรัฐในการทำธรรมาภิบาลข้อมูลระดับองค์กร
(โครงสร้าง บทบาท กระบวนการ สภาพแวดล้อม กฎเกณฑ์ และตัวชี้วัด) ไม่ได้นิยามเทคนิค
การแปลงข้อมูลใด ๆ การจับคู่ต่อไปนี้จึงบอกว่า AI Guard **ไปเสริมการปฏิบัติข้อไหน
ของกรอบ** เมื่อหน่วยงานที่ใช้กรอบนี้ต้องจัดการเอกสารที่มีข้อมูลส่วนบุคคล

| practice ใน มรด. 6:2566 (หน้า PDF) | สิ่งที่ AI Guard เสริมได้จริง |
|---|---|
| หมวดหมู่ข้อมูล 5 หมวด ซึ่งรวม **ข้อมูลส่วนบุคคล (Personal Data)** นิยามตามระบุตัวได้ทางตรง/ทางอ้อม (หน้า 21) และการจัดระดับชั้นข้อมูล Open/Private/Confidential/Secret/Top Secret (หน้า 16, 70-71 ซึ่งมอบรายละเอียดให้ มสพร. 8-2565) | `POST /api/analyze` และ `ai_guard.py report` ตรวจว่าเอกสารหนึ่งมีข้อมูลส่วนบุคคลชนิดใดกี่รายการ พร้อมคะแนนความเสี่ยง ช่วยหน่วยงานตัดสินว่าเอกสารเข้าหมวดข้อมูลส่วนบุคคลและควรได้ระดับชั้นใด การตัดสินระดับชั้นเองยังเป็นของหน่วยงานตามหลักเกณฑ์ มสพร. 8-2565 ซึ่งเอกสารนี้ไม่ได้ทบทวน |
| **Data Security and Privacy** (หน้า 26) ห้ามเปิดเผยเกินวัตถุประสงค์เว้นแต่ได้รับความยินยอมหรือมีกฎหมายรองรับ | โหมด token/surrogate และ pre-send guard ของ CLI ลดการเปิดเผยต่อผู้ให้บริการ AI ภายนอก แต่ HTTP/worker ยังมี residual-warning gap และ explicit TNER รับ raw pre-mask chunks; จึงต้องถือเป็นมาตรการเสริมที่มีขอบเขต ไม่ใช่คำรับรองว่าไม่มี PII ออกไปหรือว่าหน่วยงาน "ผ่าน" ข้อนี้โดยอัตโนมัติ |
| **Data Breach** ถูกนิยามเป็นความเสี่ยงที่ต้องจัดการอย่างเป็นระบบ (หน้า 61) โดยกรอบไม่ได้ให้ขั้นตอนรับมือหรือ timeline | `ai_guard.py breach assess` สแกนชุดไฟล์ที่ได้รับผลกระทบแล้วสรุปชนิด จำนวน และช่วงประมาณผู้ได้รับผลกระทบแบบมีที่มา เพื่อให้ผู้ควบคุมร่างแจ้ง สคส. ใน 72 ชั่วโมงตาม PDPA มาตรา 37(4) จากหลักฐานจริง (ตัว timeline มาจาก PDPA ไม่ใช่จาก มรด.) |
| บทบาท **Data Agents** มีหน้าที่ "รายงานบันทึกกิจกรรมการประมวลผลข้อมูล" (หน้า 17, 33) โดยกรอบไม่ได้กำหนดรูปแบบบันทึก | `ai_guard.py receipt issue|verify` ออกสลิปหลักฐานการประมวลผลต่อครั้งตาม PDPA มาตรา 39 ที่ตรวจซ้ำได้ด้วยการ rerun โดยไม่เก็บค่า PII ใด ๆ ในสลิป เป็นรูปธรรมหนึ่งของหน้าที่รายงานบันทึกดังกล่าวในบริบทเอกสารเดี่ยว (ไม่ใช่ RoPA สะสม โดยเจตนา) |
| สิทธิเจ้าของข้อมูล — มรด. 6:2566 **ไม่มีหัวข้อสิทธิเจ้าของข้อมูลหรือ DSAR** (พบเพียง consent ประกอบหลัก purpose limitation หน้า 26, 77) | `ai_guard.py dsar locate` ตอบโจทย์นี้จาก PDPA มาตรา 30 โดยตรง (หาว่าเอกสารใดกล่าวถึงผู้ร้อง) การจับคู่ข้อนี้จึงชี้ไปที่ PDPA ไม่ใช่ มรด. |
| **มิติด้านคุ้มครองข้อมูลให้มีความปลอดภัยและมีความเป็นส่วนตัว** (4.5.4 หน้า 77) ซึ่งกรอบชี้ออกไปยังแนวทางภายนอก (NCSA, MDES) | เครื่องมือทั้งชุดของ AI Guard อยู่ในมิตินี้ คือเป็นเครื่องมือเชิงเทคนิคที่หน่วยงานหยิบไปใช้ได้เมื่อ operationalize มิติ 4.5.4 กับเอกสารข้อความและ PDF |

## ข้อจำกัดของเอกสารนี้

- ไม่มีการอ้าง conformance กับมาตรฐานใด และไม่มีบุคคลที่สามตรวจประเมิน
- การจับคู่ ISO 20889 ในส่วน Clause 8-12 และ Annex อ้างได้เฉพาะระดับชื่อหัวข้อ
  เพราะเข้าถึงเนื้อความไม่ได้ หากได้เอกสารฉบับเต็มมาภายหลัง ควรทบทวนตาราง 1.1
  กับเนื้อความจริงอีกครั้ง โดยเฉพาะนิยามละเอียดของ masking (9.3.2) และ Annex C
