# ใบรับรองการประมวลผล มาตรา 39 — ใบต่อครั้ง ยืนยันด้วยการรันซ้ำ

วันที่ 2026-07-29 สถานะ accepted

## ปัญหา

พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล มาตรา 39 ให้ผู้ควบคุมข้อมูลเก็บบันทึกรายการกิจกรรม
การประมวลผล องค์กรที่เอา AI Guard ไปใช้จึงต้องตอบให้ได้ว่าเอกสารฉบับไหนถูกประมวลผล
เมื่อไร ด้วยระบบเวอร์ชันอะไร และเจอข้อมูลส่วนบุคคลกี่รายการ ตอนนี้ระบบทำงานเสร็จแล้ว
ไม่เหลืออะไรให้ชี้เลย

## ทางที่ไม่เลือก และเหตุผล

**ทะเบียนสะสมแบบ RoPA** เป็นการอ่านมาตรา 39 ที่ตรงตัวที่สุด และเป็นทางที่ขัดกับตัว
ผลิตภัณฑ์มากที่สุด vault อยู่ในหน่วยความจำอย่างเดียว เส้นทาง hosted เป็น stateless
ตามสัญญาที่เซ็นไว้ และไม่มีอะไรเกี่ยวกับเอกสารรอดข้ามคำขอ การเปิดทะเบียนแปลว่าเริ่มเก็บ
สิ่งที่ประกาศไว้ว่าไม่เก็บ แลกความสามารถในการพิมพ์รายงานกับคำสัญญาหลักของโครงการ

**ลายเซ็นดิจิทัล** พิสูจน์ว่าใครออกใบ แต่ไม่พิสูจน์ว่าใบนั้นตรงกับความจริง ใบที่เซ็นแล้ว
แต่กรอกตัวเลขผิดก็ยังผ่านการตรวจลายเซ็น และมันต้องมีกุญแจให้เก็บ ซึ่งเป็นความลับเพิ่มอีก
หนึ่งอย่างที่เครื่องมือ local-first ไม่ควรขอจากผู้ใช้

## สิ่งที่ตัดสิน

**ใบต่อครั้ง** การรันหนึ่งครั้งออกใบได้หนึ่งใบ ผู้ใช้เก็บใบไว้ข้างไฟล์ของตัวเอง ใบบันทึกว่า
ประมวลผลอะไร เจอกี่รายการชนิดไหน ด้วยเวอร์ชันและ engine อะไร เมื่อไร มันบันทึกการ
ประมวลผล ไม่ได้บันทึกตัวบุคคล

**ยืนยันด้วยการรันซ้ำ** ใบพกค่าแฮชสองค่า ค่าหนึ่งของไบต์ต้นทาง อีกค่าหนึ่งของผลการตรวจ
เอาใบกับไฟล์ต้นฉบับมาให้ `verify` มันจะรันไปป์ไลน์เดิมซ้ำแล้วเทียบ ถ้าไฟล์เป็นไฟล์เดิมและ
ระบบยังเห็นสิ่งเดิมในไฟล์นั้น ค่าแฮชจะตรง จุดยืนเดียวกับที่
[ADR เรื่อง distribution](2026-07-29-store-distribution-and-signing.md) ใช้กับตัวติดตั้ง
คือความน่าเชื่อถือมาจากการตรวจสอบได้ ไม่ใช่จากใบรับรอง

**สองค่าแฮชแยกกัน ไม่ยุบเป็นค่าเดียว** เพื่อให้แยกออกว่า "นี่ไม่ใช่เอกสารที่ใบนี้ออกให้"
กับ "เอกสารเดิม แต่ระบบเห็นต่างจากเดิมแล้ว" ถ้ายุบเป็นค่าเดียว การอัปเกรดเวอร์ชันจะดู
เหมือนการสลับไฟล์

**ขอบเขต v1** แกน + CLI ที่ทำได้ทั้งออกใบและตรวจใบ + PDF ภาษาไทย **ไม่มี API endpoint**
ตัวตรวจอยู่ในรอบแรกโดยตั้งใจ เพราะใบที่ไม่มีใครตรวจได้คือคำกล่าวอ้าง ไม่ใช่บันทึก

## สิ่งที่จงใจไม่อยู่ในค่าแฮชของผล

- `entity_id` เป็น UUID4 ใหม่ทุกครั้งที่รัน ถ้าเอาเข้าไปด้วย ใบทุกใบจะยืนยันไม่ผ่าน
  ตั้งแต่วินาทีแรกโดยโครงสร้าง
- `score` เป็นค่าความมั่นใจภายในของตัวตรวจ PyThaiNLP ออก patch release แล้ว float
  ขยับโดยที่ไม่มี span ไหนขยับเลยก็เป็นไปได้ ใบที่ตกด้วยเหตุนี้จะสอนคนอ่านให้เลิกสนใจ
  ผลตรวจ สิ่งที่ใบรับรองยืนยันคือ span ไหนชนิดอะไรถูกนับเป็นข้อมูลส่วนบุคคล ซึ่งเป็นตัว
  ตัดสินว่าอะไรจะถูกปิด

ค่าแฮชคำนวณจาก span กับชนิดที่เรียงแล้ว ลำดับของตัวตรวจจึงเปลี่ยนค่าไม่ได้ และไม่มี
บรรทัดไหนในโมดูลนี้อ่านค่าข้อความของ entity เลย

## หลักฐาน

ข้ออ้างที่ดีไซน์นี้ตั้งอยู่บนมันคือ input เดิมให้ค่าแฮชเดิม วัดแล้วไม่ใช่สมมติ
`tests/test_receipt.py` รันสามโปรเซสแยกกันด้วย `PYTHONHASHSEED` เป็น 0, 1 และ
`random` แล้วบังคับให้ได้ค่าเดียวกัน พร้อมกันนั้นบังคับว่าค่าที่ได้ต้องไม่ใช่ค่าแฮชของผลว่าง
เพราะสามโปรเซสที่ไม่เจออะไรเลยก็จะตรงกันเหมือนกันด้วยเหตุผลที่ผิด

เดินเส้นทาง CLI จริงกับเอกสารไทยสังเคราะห์ ออกใบที่มี 5 entity ตรวจแล้วผ่าน (exit 0)
เติมข้อความเข้าไปหนึ่งบรรทัดแล้วตรวจใหม่ได้ `source_mismatch` (exit 1)

## บันทึกเพิ่ม 29 ก.ค. หลังรีวิวอิสระ

รีวิวเชิงโจมตีจาก context แยก (ตามที่ `AGENTS.md` กำหนดสำหรับงานระดับนี้) พบว่า
ตัวตรวจรอบแรกเทียบแค่ค่าแฮชสองค่า ส่วนตัวเลขที่มนุษย์อ่านจริงบนใบ คือจำนวน entity
จำนวนแยกชนิด ขนาดไฟล์ และชนิดเอกสาร ไม่ถูกรับรองเลย แก้ใบให้บอกว่าเจอศูนย์รายการ
แล้ว verify ยังขึ้นว่า "ยืนยันได้" ทั้งที่ตัวมันเองคำนวณเลขจริงไว้แล้วแล้วทิ้ง

รากของปัญหาไม่ใช่การลืมเทียบหกฟิลด์ แต่คือการมีสองแหล่งความจริง ตัวออกใบสร้าง
ตัวเลขชุดหนึ่ง ตัวตรวจสร้างอีกชุด แล้วเทียบกันแค่บางส่วน ตอนนี้ทั้งสองฝั่งเรียก
`_claims()` ตัวเดียวกัน ฟิลด์ที่เพิ่มเข้ามาภายหลังจึงถูกตรวจโดยโครงสร้าง ไม่ใช่โดยการ
ที่ใครสักคนจำได้ว่าต้องไปเพิ่มการเทียบ

สิ่งที่แก้พร้อมกันจากรีวิวเดียวกัน

- ใบ PDF เคยพิมพ์ว่า "ไม่มีค่าข้อมูลส่วนบุคคลใดอยู่ในเอกสาร" แบบไม่มีเงื่อนไข
  ทั้งที่ `--purpose` และ `--controller` เป็นข้อความที่ผู้ใช้พิมพ์เองและถูกวาดลงหน้า
  เดียวกันโดยไม่ผ่านตัวกรอง คำรับรองถูกจำกัดขอบเขตให้ตรงกับความจริงแล้ว
- `environment` เพิ่มเวอร์ชัน PyThaiNLP เพราะ `requirements.txt` ใช้ floor แบบหลวม
  เครื่องสองเครื่องที่เวอร์ชันระบบเท่ากันจึงมี CRF คนละรุ่นได้ ซึ่งเป็นสาเหตุที่น่าจะ
  เกิดบ่อยที่สุดของ `result_mismatch` และเดิมเป็นสาเหตุเดียวที่ใบมองไม่เห็น
- ออกใบแฮชไฟล์สองรอบ คร่อมไปป์ไลน์ ถ้าไบต์เปลี่ยนระหว่างทางจะไม่ออกใบเลย ดีกว่าออกใบ
  ที่แฮชอธิบายไบต์ใหม่แต่ผลอธิบายไบต์เก่า
- ไบต์ตรงแต่ประมวลผลซ้ำไม่ได้ (เช่นเปลี่ยนนามสกุลไฟล์) ได้ผลลัพธ์ของตัวเองชื่อ
  `recompute_failed` แทนที่จะหลุดออกมาเป็นข้อความที่อ่านแล้วเหมือนเครื่องมือพัง

## สิ่งที่ใบนี้ไม่ได้ทำ

มาตรา 39 มีรายการที่เครื่องมือตอบแทนผู้ใช้ไม่ได้ ผู้ควบคุมข้อมูล วัตถุประสงค์ ระยะเวลา
เก็บรักษา สิทธิของเจ้าของข้อมูล ระบบรับ `--purpose` กับ `--controller` จากผู้ใช้และ
ปล่อยว่างถ้าไม่ได้ระบุ แทนที่จะเติมค่าที่ฟังดูเข้าท่าให้ ใบรับรองที่กรอกคำกล่าวอ้างซึ่งไม่มีใคร
พูดจริง แย่กว่าใบที่ยอมรับว่ายังไม่มีข้อมูลตรงนั้น
