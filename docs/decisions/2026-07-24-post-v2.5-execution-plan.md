# Post-v2.5 AI for Thai Execution Plan

- Date: 2026-07-24
- Status: owner-confirmed; execution in progress
- Execution window: 2026-07-24 through the presentation on 2026-08-19
- Product baseline: released `2.5.0`

This is a time-bounded execution plan, not a current-state document and not a
replacement for [ROADMAP.md](../../ROADMAP.md). Current evidence remains in
[project-status.md](../project-status.md); functional gates remain in the
[acceptance checklist](../acceptance/README.md).

## Fixed dates and decision

The owner-approved
[Roadmap v2 decision](2026-07-17-roadmap-v2-design.md) records the AI for Thai
requirements: complete deployment by **2026-08-17** and present on
**2026-08-19**. The presentation slot is 10 minutes followed by 5 minutes of
questions.

The plan therefore makes these decisions:

1. Official AI for Thai acceptance is the critical path.
2. All repository work that does not require the official account/specification
   is targeted for one 48-hour Codex sprint ending 2026-07-26.
3. No new product feature merges into the competition candidate before the
   official platform path and candidate regression are green.
4. If the 48-hour gate is green while platform access remains externally
   blocked, the owner may approve Policy Gateway work on an isolated branch. It
   must not destabilize or silently enter the competition candidate.
5. Accuracy tuning and benchmark expansion remain under ROADMAP Phase 3.
6. Office enhancement work remains paused; the accepted `2.5.0` Office scope
   receives only blocker or security fixes.
7. The release candidate freezes after 2026-08-10. From 2026-08-11 onward,
   only deployment blockers and security defects may change code.

The dates after the first 48 hours are external gates, waiting buffer, official
acceptance, and human rehearsal time. They are not estimates of how long Codex
needs to write the repository changes.

## 48-hour Codex sprint

Target: finish every non-externally-blocked repository task by
**2026-07-26**.

| Active-work window | Parallel outcome |
|---|---|
| Hours 0-8 | Exact `2.5.0` Desktop UI acceptance, evidence, and current-state reconciliation; platform missing-field request prepared in parallel. |
| Hours 8-24 | Versioned provisional envelope, deterministic emulator, transport boundary, and core contract tests. |
| Hours 24-36 | Duplicate/retry/timeout/crash/payload/concurrency cases, honeytoken log audit, and local resource measurements. |
| Hours 36-44 | Full CI-equivalent suite, Docker smoke, and repeatable live Pathumma/TNER acceptance. |
| Hours 44-48 | Documentation synchronization, accepted GitHub issue set, clean candidate handoff, and explicit external-blocker ledger. |

The sprint may use parallel agents for disjoint test, documentation, and
platform-emulator scopes. One implementation owner retains responsibility for
shared core and API changes.

The sprint cannot manufacture:

- an unissued platform username, account, or deployment specification;
- official-platform runtime and log evidence;
- a meaningful soak period by merely sleeping;
- two human presentation rehearsals.

Those items remain calendar gates even when all repository work is already
complete.

## Workstream A — Immediate closure and platform access

Target: **Hours 0-8 of the 48-hour sprint**

### Repository work

- Complete the exact installed `2.5.0` Desktop UI checklist:
  - launch, version, and sidecar health;
  - token and surrogate Mask/Restore;
  - PDPA report generation and opening;
  - PDF redaction and source-text recovery check;
  - settings, audit view, global hotkey, and updater;
  - close/reopen and port release.
- Record installer filename, SHA-256, OS, version, pass/fail, and
  synthetic-only screenshots.
- Reconcile the Desktop row in `docs/project-status.md` with this exact
  evidence.
- Keep `VERSION` at `2.5.0` unless acceptance finds a compatible defect that
  actually requires `2.5.1`.

### Owner/platform coordination

- Follow up with AI for Thai for the missing username/account and official
  deployment specification.
- Ask for the job envelope, authentication, registry, secrets, timeout, retry,
  acknowledgement, payload, network, logging, and resource policies.
- Record each unanswered field as `unknown`; do not convert assumptions into a
  contract.
- If nothing is received by **2026-07-28**, send a written follow-up containing
  the missing-field checklist.
- If the account/specification is still unavailable by **2026-08-01**, escalate
  the deadline risk to the platform contact and retain the response as
  non-PII project evidence.

### Exit gate

- Desktop acceptance truth is reconciled.
- The official platform request and all unknown fields are documented.
- Every accepted implementation item below has a reviewable GitHub issue after
  the owner confirms this plan.

## Workstream B — Emulator and adapter readiness

Target: **Hours 8-36 of the 48-hour sprint**

This work proceeds even if platform access remains blocked.

- Keep the current HTTP-poll transport explicitly provisional.
- Isolate the transport from the stable queue operations.
- Version the provisional job envelope in contract fixtures.
- Build a deterministic platform emulator covering:
  - duplicate delivery and idempotency;
  - acknowledgement, negative acknowledgement, and retry;
  - malformed and unsupported jobs;
  - provider timeout and worker failure;
  - payload limits;
  - sequential and concurrent jobs;
  - crash recovery without duplicate external side effects.
- Run a synthetic PII honeytoken scan over application and emulator-visible
  logs.
- Record container startup, image size, CPU, peak RAM, and operation latency as
  local evidence only.
- When the official specification arrives, implement only the transport and
  configuration delta. Do not duplicate or rewrite detection, anonymization,
  vault, leak-guard, or provider logic.

### Exit gate

- Emulator cases run repeatedly in CI.
- Retry or duplicate delivery produces no duplicate provider side effect.
- No mapping or honeytoken appears in logs, results, or error metadata.
- The official contract delta is listed field by field.
- Be ready for the first official deployment at the end of the 48-hour sprint.
  Attempt it immediately when access permits, with **2026-08-03** as the latest
  planned first-attempt date. If access does not permit it, retain an explicit
  external-blocker status rather than claiming deployment acceptance.

## Workstream C — Official acceptance and full verification

Target: **immediately when access arrives; complete no later than
2026-08-10**

### Official platform path

After the account and specification arrive:

1. build and push the official image;
2. boot the service with platform-managed secrets;
3. complete one valid Thai UTF-8 job;
4. test malformed, duplicate, timeout, payload-limit, provider-failure, crash,
   retry, and concurrent-job behavior;
5. run a repeatable soak;
6. inspect application and platform-visible logs with a synthetic honeytoken;
7. record CPU, RAM, timeout, payload, retry, and logging behavior on official
   infrastructure.

Official deployment is accepted only when the job succeeds, failure behavior
matches the issued contract, and no PII-bearing log or mapping export is found.

### Candidate regression

- Run the full automated suite and Docker smoke from a clean candidate.
- Repeat live Pathumma and TNER acceptance using synthetic PII.
- Re-run only the real storefront paths affected by a candidate code change.
- Verify documentation, image/configuration, demo script, and running behavior
  describe the same contract.

### Hard escalation

If no successful official deployment exists by **2026-08-08**, stop all
non-platform coding and work only on the platform blocker, its documented
fallback, and coordination with AI for Thai.

### Exit gate

- Candidate verification is green.
- Official deployment acceptance is complete, or the precise external blocker
  and all completed readiness evidence are recorded without overclaiming.
- Feature freeze begins after **2026-08-10**.

## Workstream D — Presentation freeze

Target: **2026-08-11 through 2026-08-17**

- Prepare one fixed synthetic demo fixture and exact click sequence.
- Build the 10-minute story:
  problem → privacy risk → AI Guard → protected Pathumma flow → evidence.
- Record an offline fallback video.
- Keep a fake-provider fallback that demonstrates the privacy flow without
  network access.
- Prepare answers covering PDPA scope, vault boundaries, provider visibility,
  prompt-injection limitations, accuracy, and deployment assumptions.
- Complete at least two rehearsals on the presentation machine.
- Accept only deployment-blocking or security fixes; every such fix must repeat
  its affected acceptance path.

The official deployment hard gate is **2026-08-17**. Presentation is
**2026-08-19**.

## Version lines

The three version lines remain independent, as defined in
[versioning-proposal.md](../versioning-proposal.md):

| Scope | Next value | Rule during this plan |
|---|---:|---|
| Desktop/extension/product | `2.5.0` | Stay unchanged; use `2.5.1` only for an accepted compatible fix. |
| AI for Thai service | `0.1.0` | Introduce a separate source only after the platform states where the value must appear. |
| Public API contract | `1` | Change only for an incompatible caller contract. |

Do not reset the product to `0.1.x`, pre-bump a release, move a published tag,
or duplicate the service version across files before the official requirement
exists.

## Policy Gateway decision

At the 48-hour gate on **2026-07-26**:

- if non-blocked work is not green, finish it before opening new scope;
- if official access is available, prioritize the real deployment and
  acceptance;
- if non-blocked work is green but access remains externally blocked, the owner
  may approve Policy Gateway development on an isolated branch;
- do not merge that branch into the competition candidate unless its acceptance
  passes before feature freeze and it does not put official deployment at risk.

On or after **2026-08-20**, use user and judge feedback for the final merge,
redesign, or rejection decision. Policy Gateway remains the leading candidate:
named privacy policies plus a protected integration contract for other
applications. If approved as shipped additive scope, it may target `2.6.0`.

Benchmark and detection-quality work continues under ROADMAP Phase 3. This
execution plan intentionally does not duplicate that phase's scorer, corpus,
engine-comparison, or public-claim rules.
