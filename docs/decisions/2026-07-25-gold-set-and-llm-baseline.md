# Gold set v3 and the LLM-as-detector baseline

- วันที่ 2026-07-25
- ต่อจาก [2026-07-13 Thai PII recall benchmark](2026-07-13-thai-pii-recall-benchmark-design.md)
  ซึ่งวาง scorer, corpus สังเคราะห์ และกฎการรายงานไว้แล้ว เอกสารนี้บันทึกเฉพาะ
  สิ่งที่เปลี่ยนในรอบนี้ ไม่ทับของเดิม

## ปัญหาที่ทำให้ต้องขยาย

ชุดทองเดิมมี 66 เอกสาร 81 entity ซึ่งเล็กเกินกว่าจะรายงานผลรายชนิดได้ THAI_ID มี 2 ตัว
ส่วน CREDIT_CARD PASSPORT STUDENT_ID VEHICLE_PLATE DATE_OF_BIRTH มีอย่างละ 1 ตัว
การรายงาน recall 1.000 ที่ n=1 ไม่มีความหมายทางสถิติ และชุดเดิมไม่มีเอกสารที่ปราศจาก PII
เลยแม้แต่ชิ้นเดียว จึงวัด false positive ไม่ได้

## สิ่งที่เปลี่ยน

### ชุดทอง 252 เอกสาร 641 entity

เอกสารเดิม 66 ชิ้นคงอยู่ไม่แก้ข้อความและไม่แก้ label เพื่อให้ตัวเลขที่รายงานไว้แล้ว
ตรวจย้อนได้ ของใหม่อิงโครงสร้างเอกสารสาธารณะไทย ทุกชนิดถึง n>=20 และช่วงความเชื่อมั่น
95% ของ overall แคบลงจาก 0.071 เหลือ 0.054

ข้อมูลย้ายจาก literal ใน `benchmark/gold.py` ไปที่ `benchmark/data/gold.jsonl`
`gold.py` เหลือ parser กับ loader `.gitignore` มีข้อยกเว้นให้ไฟล์นี้ เพราะกฎ `*.jsonl`
เดิมมีไว้กัน audit log ที่มี pseudonym ส่วนไฟล์นี้เป็น source data ที่ค่าทุกตัวเป็นของปลอม

slice ที่เพิ่ม

| slice | ทำไมถึงมี |
|---|---|
| `gov_form` `medical` `finance` `education` | สัดส่วนตามเอกสารจริง ใช้รายงาน overall |
| `long_form` | เอกสารยาวเกิน 500 ตัวอักษร เปิดเส้นทาง stride-chunk windowing ที่ไม่เคยถูกวัด |
| `student_id_varied` | probe แยกแกนรูปแบบทีละแกน ให้การพลาดบอกสาเหตุตัวเอง |
| `negative` | เอกสารไม่มี PII เลย วัด false positive ได้เป็นครั้งแรก |

`negative` ใส่เฉพาะของที่ไม่ควรถูกจับเด็ดขาด เช่น เลขที่หนังสือราชการ เลขใบเสร็จ
เลขมาตรากฎหมาย ISBN จงใจไม่เอาชื่อจังหวัดหรือชื่อหน่วยงานลอยๆ มา เพราะระบบตั้งใจจับ
เป็น quasi-identifier ตาม invariant recall > precision การนับว่ามันผิดคือการวัดผิด

scorer แก้จุดเดียว กลุ่มที่ไม่มี gold span เลยจะรายงาน `false_positives` กับ
`clean_doc_rate` แทน recall 0.0 ซึ่งอ่านเป็นการพลาดยับทั้งที่อาจสะอาดหมด

### สิ่งที่ชุดใหม่ขุดเจอ

1. **chunking ไม่พัง** `long_form` ให้ recall 0.951 สูงที่สุดในทุก slice ทั้งที่มี 27 span
   อยู่หลังขอบ chunk เป็นผลลบที่มีค่า เพราะก่อนหน้านี้เส้นทางนี้ไม่มีอะไรวัดเลย
2. **STUDENT_ID มีบั๊กจริงสองจุด** แก้แล้วใน `fp_detector.py` รอบนี้ ดูหัวข้อถัดไป
3. **negative slice สะอาดแค่ 16 จาก 45** false positive 43 จุด เป็นราคาของ recall-first
   ที่วัดเป็นตัวเลขได้แล้ว

### บั๊ก STUDENT_ID ที่แก้

เลขสิบหลักที่เป็นรหัสนักศึกษาถูก `_RE_BANK_ACCOUNT_2` จับด้วย ซึ่ง emit ที่ score 1.0
และไม่ต้องมี cue เลย ขณะที่ STUDENT_ID ถูก cue-gate ไว้ที่ 0.8 dedup จึงยก span
ให้ BANK_ACCOUNT ทุกครั้งแม้มีคำว่ารหัสนักศึกษาอยู่ข้างหน้าตรงๆ วัดได้ 0 จาก 8
แก้ด้วย `_disambiguate_bank_student` ที่ตัดสินด้วย cue ใกล้ตัวเลขที่สุด
กฎเดียวกับ `_disambiguate_bank_phone` ที่มีอยู่แล้วสำหรับคู่ PHONE/BANK

รายการ cue เดิมมี นักศึกษา กับ นิสิต แต่ไม่มี นักเรียน กับ ผู้เรียน เลขประจำตัวนักเรียน
จึงตกไปเป็น ID_NUMBER จงใจไม่ใส่คำว่า รหัส เดี่ยวๆ เพราะมันนำหน้ารหัสสินค้า รหัสวิชา
รหัสหลักสูตร ซึ่ง ID_NUMBER ปิดให้อยู่แล้ว การรับเข้ามาจึงไม่ได้ความปลอดภัยเพิ่ม
แลกกับป้ายที่โกหก

ผล STUDENT_ID recall 0.333 เป็น 0.509 ที่ precision 1.000 · BANK_ACCOUNT precision
0.660 เป็น 0.761 ที่ recall 1.000 · overall 0.860 เป็น 0.875 · negative slice เท่าเดิม
คือไม่ได้สร้าง false positive ใหม่ · corpus สังเคราะห์ยัง 1.000

### baseline ภายนอก

`benchmark/llm_strategy.py` กับ `benchmark/llm_providers.py` ให้โมเดลแชตทำหน้าที่
ตัวตรวจจับบนชุดเดียวกัน เพื่อตอบว่าการส่งข้อความออกไปให้โมเดลใหญ่ซื้ออะไรได้บ้าง
โมเดลได้รับรายชื่อชนิดตรงกับ gold พร้อมนิยาม และถูกขอแค่ค่า ไม่ต้องนับ offset เอง
เพราะการให้โมเดลนับตำแหน่งตัวอักษรคือการวัดเลขคณิต ไม่ใช่การสกัดข้อมูล
span คำนวณฝั่งเราด้วยกฎ claim ยาวก่อนไม่ทับกัน กฎเดียวกับ `reverse_mapper`

รายงานสองมุมเสมอ มุม strict นับเฉพาะชนิดในรายการ มุม type-agnostic เปลี่ยน label
ทั้งสองฝั่งเป็นชนิดเดียวแล้วให้คะแนนใหม่ เพื่อแยก "หาเจอไหม" ออกจาก "เรียกชื่อถูกไหม"
Pathumma ทำให้เห็นว่าจำเป็น เพราะมันตอบด้วยชื่อฟิลด์ภาษาไทยเป็น type
คิดชื่อชนิดขึ้นเองกว่า 150 แบบ ตัวเลข strict ของมันจึงวัดการทำตามคำสั่งปนอยู่

คำตอบดิบถูก cache รายเอกสาร การแก้ prompt หรือ scorer แล้ว re-score จึงไม่เสียโควตา

## สิ่งที่ยังไม่ทำ

- ค่าความสอดคล้องระหว่างผู้ label สองคน ชุดนี้ยัง label โดยแหล่งเดียว
- bootstrap confidence interval ในตัว runner ตอนนี้คำนวณนอกเครื่องมือ
- รหัสนักศึกษาที่มีขีดคั่นยังถูกจัดเป็น DATE การให้ `_RE_STUDENT_ID` รับตัวคั่น
  จะแลกหนึ่งตัวอย่างกับ false positive วันที่ทั้งกอง จึงปล่อยไว้และบันทึกแทน

## กฎการอ้างตัวเลขจากชุดนี้

ต้องระบุขนาดชุดและการกระจายรายชนิดทุกครั้ง ห้ามยกตัวเลขจาก corpus สังเคราะห์
เป็นผลหลัก และต้องบอกว่าเอกสารเป็นการประกอบขึ้นตามรูปแบบมาตรฐาน ไม่ใช่เอกสารจริง
ที่เก็บจากการใช้งาน gold ยังเป็น diagnostic ไม่ใช่ CI gate ไม่ตั้ง floor ให้เขียว
